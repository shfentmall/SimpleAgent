# /ship：写交接简报，交给 shipper

上线步骤在 [shipper](../../agents/shipper.md) 里，主会话不自己跑。

原因是 token：/ship 一般接在开发会话末尾，上下文已经 10 万～70 万 token，主会话里每个调用都要重读一遍，
连一次 `git status` 都要几万 token。闲置超过 1 小时再敲 /ship，第一个调用还要把整段上下文重新写进缓存。
shipper 从空上下文开始，同样的步骤便宜得多。

主会话只做两件事：写交接简报、转告结果。**不要先跑 git 命令、读文件或者复查。**

## 1. 派出 shipper

直接调用 Agent 工具：`subagent_type: shipper`，`run_in_background: false`，`prompt` 用下面的格式，30 行以内。

```
工作目录：<当前目录的绝对路径>（worktree 的话再写主目录路径）
分支：<分支名>
用户的补充说明：<照抄下面的 /ship 参数，为空写「无」>

这次做了什么：
- <一到三条，用功能的话说>

开发时已经验证过的：
- 自动检查：<最后一次 ruff / pytest 的结果，之后又改过哪些文件>
- 手动验证：<在浏览器或 CLI 里走过哪些操作，结果如何>

没验证过、需要 shipper 验证的：
- <没有就写「无」>

需要注意的：<已知遗留问题、别的会话也在用这个分支、不该提交的文件等；没有就写「无」>
```

- 只写对话里确实发生过的事。没把握验证过的，放进「没验证过」。
- 用户在 /ship 后面的补充说明（为空就是没有）：「$ARGUMENTS」

## 2. 转告结果

- shipper 汇报第一行是 `需要用户决定：…`：把问题转给用户，等用户回复后用 SendMessage 把决定发给同一个
  shipper，让它接着走。不要新开一个，也不要自己接手后面的步骤。
- 其他情况：把汇报原样或精简后转给用户。不要再跑 git / gh 命令复查，shipper 已经查过。
- 不要接着出原理图、写学习笔记。原理图由用户敲 `/explainer` 另外跑。
